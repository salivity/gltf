WebGL Draw Buffers: Fast Deferred glTF Rendering

Deferred rendering decouples scene geometry processing from lighting calculations, allowing WebGL applications to render complex scenes with dozens or hundreds of dynamic lights at high frame rates. When loading complex glTF 2.0 assets—which often contain intricate node hierarchies, skeletal animations, and detailed physically based rendering (PBR) materials—the primary performance bottleneck shifts to generating the geometry buffer (G-buffer). The WEBGL_draw_buffers extension accelerates this pipeline by enabling Multiple Render Targets (MRT), allowing a fragment shader to output position, normal, albedo, and material parameters into multiple textures in a single draw pass, eliminating redundant geometry evaluations.

The Bottleneck of Multi-Pass G-Buffer Generation

In baseline WebGL 1.0 without extensions, a framebuffer can only bind and write to a single color attachment at a time via gl_FragColor. To populate a standard G-buffer, the graphics pipeline requires separate textures for distinct surface properties:

  1. Surface normals and depth
  2. Base color (albedo) and ambient occlusion
  3. Metallic, roughness, and emissive values

Without MRT, an engine must re-render the entire glTF scene for every target texture. A three-target G-buffer requires three full geometry passes. Because glTF assets often contain thousands of draw calls, heavy skeletal matrices for skinned meshes, and morph target calculations, executing these operations multiple times per frame strains both the CPU (draw call overhead) and the GPU vertex processing units.

How WEBGL_draw_buffers Eliminates Redundancy

The WEBGL_draw_buffers extension introduces Multiple Render Targets to WebGL 1.0 (a capability integrated natively into the core WebGL 2.0 specification). It exposes the gl_FragData[n] array to the fragment shader and allows developers to attach multiple textures to a single framebuffer via gl.framebufferTexture2D using extended attachment points (COLOR_ATTACHMENT0_WEBGL, COLOR_ATTACHMENT1_WEBGL, etc.).

During the G-buffer pass, the application issues ext.drawBuffersWEBGL(...) to define the target array. When a glTF mesh is drawn:

  • Vertex Shading Happens Once: Mesh skinning, morph target blending, and coordinate space transformations (local-to-world-to-clip) are executed once per vertex instead of once per G-buffer layer.
  • Texture Lookups Are Consolidated: The fragment shader samples the glTF base color, normal, and metallic-roughness texture maps in a single execution step.
  • Simultaneous Output: The computed values are written directly to their corresponding textures in parallel using indexed output registers.

Mapping glTF PBR Workflows to MRT

The glTF 2.0 specification standardizes a Metallic-Roughness PBR workflow, which maps neatly into packed G-buffer layouts when using WEBGL_draw_buffers. A typical 32-bit floating-point or 8-bit RGBA texture layout utilizes three attachments:

  • Attachment 0 (Color & AO): gl_FragData[0] = vec4(albedo.rgb, occlusion);
  • Attachment 1 (Normals & Roughness): gl_FragData[1] = vec4(encodedNormal.xy, depthComponent, roughness);
  • Attachment 2 (PBR & Emissive): gl_FragData[2] = vec4(emissive.rgb, metallic);

By writing all standardized glTF surface parameters simultaneously, the expensive PBR lighting pass can be fully deferred to a subsequent screen-space pass. In that final pass, lights are rendered as screen-aligned quads or bounding volumes that sample the precomputed textures, ensuring lighting costs remain \(O(\text{lights})\) or proportional to screen coverage rather than \(O(\text{geometry} \times \text{lights})\).

Real-World Performance Impact

Using WEBGL_draw_buffers transforms the geometry stage from an \(O(N \times M)\) operation (where \(N\) is the number of render targets and \(M\) is the number of glTF primitives) into an \(O(M)\) operation. This delivers substantial real-world advantages:

  • CPU Overhead Reduction: The JavaScript engine transmits state changes, uniform updates, and draw commands once per frame per glTF mesh, mitigating the single-threaded CPU bottlenecks common in browser environments.
  • Memory Bandwidth Optimization: Reading geometry attributes (indices, positions, UVs) from GPU VRAM only once per frame reduces bus saturation, preserving bandwidth for dynamic post-processing effects such as screen-space ambient occlusion (SSAO), bloom, and tone mapping.
  • Consistent Frame Times: For animated glTF characters and rich digital twins, bounding the vertex overhead guarantees predictable frametimes critical for smooth interactive experiences across heterogeneous hardware.
