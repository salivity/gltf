glTF Streaming: Loading Assets by Camera Proximity

Streaming glTF engines manage vast 3D scenes by dynamically loading and unloading assets according to the viewer's camera position. By evaluating spatial proximity, screen-space metrics, and hierarchical data structures, these engines ensure that high-resolution meshes and textures are loaded only when visible and close to the camera, while distant or out-of-view objects are swapped for lower-detail proxies or purged from memory entirely. This dynamic pipeline preserves memory budgets, minimizes network bandwidth, and maintains smooth frame rates across diverse hardware.

Spatial Partitioning and Bounding Volumes

To rapidly evaluate proximity without checking thousands of objects individually each frame, engines organize the 3D scene into spatial data structures such as octrees, bounding volume hierarchies (BVH), or geospatial grids like 3D Tiles.

Each glTF node or external chunk is wrapped in a simplified mathematical boundary, typically an axis-aligned bounding box (AABB) or a bounding sphere. At runtime, the engine calculates the distance between the camera position vector and the closest point on each bounding volume. If a bounding volume falls completely outside the camera's view frustum, it is culled immediately from proximity calculations, saving processing cycles.

Distance Metrics and Screen Space Error (SSE)

Engines typically use one of two methods to determine when to trigger asset state changes:

  1. Euclidean Distance: The straight-line distance between the camera and the object's origin or bounding center. If the distance falls below a defined threshold (\(d_{load}\)), the asset is queued for download and rendering.
  2. Screen Space Error (SSE): A more advanced metric that factors in camera field-of-view (FOV), viewport resolution, and distance. SSE estimates the geometric deviation between a simplified model and the full-resolution model in terms of screen pixels. When the estimated error exceeds a defined pixel threshold, the engine requests a higher-fidelity asset.

Levels of Detail (LOD) and glTF Extensions

Streaming implementations rarely load an asset from zero to full resolution in a single step. Instead, they rely on hierarchical Levels of Detail (HLOD).

glTF supports LOD setups natively through vendor extensions like MSFT_lod or via composite specifications such as OGC 3D Tiles (which uses glTF as its payload format). As the camera approaches an object, the engine requests increasingly detailed glTF files or buffers:

  • Far Distance: Lightweight bounding boxes, single-triangle billboards, or heavily decimated meshes with minimal texture maps.
  • Mid Distance: Simplified geometry with downsampled or compressed textures (e.g., Basis Universal / KTX2 format).
  • Near Distance: Full-fidelity geometry with complex PBR material maps and normal buffers.

Asynchronous Fetching and GPU Uploading

Loading assets synchronously freezes the render thread, causing frame drops. Modern streaming engines handle glTF retrieval through a non-blocking asynchronous pipeline:

  1. Network Fetch: Binary glTF chunks (.glb or external .bin and image files) are retrieved using background network requests.
  2. Worker Decoding: Web Workers or secondary CPU threads parse the JSON hierarchy, unpack Draco or Meshopt compressed geometry, and decode texture data.
  3. Staged GPU Ingestion: Once decoded, buffers are transferred to the GPU using asynchronous memory staging (such as createImageBitmap and asynchronous buffer uploads in WebGL/WebGPU) over several frames to prevent visual stutter.

Unloading Mechanisms and Thrashing Prevention

When the camera retreats beyond an object's threshold, the engine marks the asset for eviction to prevent memory overflow. To handle unloading efficiently, engines implement two key strategies:

  • Hysteresis Margins: To prevent "thrashing"—a rapid loop of loading and unloading when a camera hovers near an activation boundary—engines use different thresholds for loading and unloading. For instance, an asset might load at 50 meters from the camera but only unload when the camera retreats past 65 meters.
  • Least Recently Used (LRU) Cache: Assets flagged for eviction are often kept in a memory cache rather than immediately destroyed. If the camera returns quickly, the engine retrieves the asset from cache without re-downloading. When the total memory budget is reached, the least recently viewed assets are permanently disposed of, destroying their GPU buffers, textures, and shader programs.
