Common glTF Buffer Alignment Errors Explained

The glTF 2.0 specification enforces strict data alignment rules to guarantee that binary data can be loaded directly into GPU buffers without costly CPU-side re-indexing or copying. When these rules are broken, the official glTF Validator flags specific buffer alignment errors that prevent models from rendering properly or passing asset pipelines. This guide breaks down the common buffer alignment errors flagged by the glTF Validator, explaining why they occur and how to resolve them.

BufferView Byte Offset Misalignment

The glTF 2.0 specification mandates that every bufferView.byteOffset must be a multiple of 4.

The glTF Validator catches this issue through errors like:

  • BUFFER_VIEW_BYTE_OFFSET_NOT_DIVISIBLE_BY_4

This error commonly occurs when packing variable-length binary payloads—such as animation tracks or compressed vertex attributes—directly behind one another without padding. To fix it, you must insert zero-padding bytes at the end of the preceding chunk so that the starting byteOffset of the next bufferView is evenly divisible by 4.

Accessor Byte Offset Misalignment

An accessor reads data from a bufferView. The accessor.byteOffset must be an exact multiple of the data type size defined by its componentType.

The glTF Validator reports this with:

  • ACCESSOR_BYTE_OFFSET_ALIGNMENT

For example:

  • FLOAT (5126) is 4 bytes; its byteOffset must be divisible by 4.
  • UNSIGNED_SHORT (5123) is 2 bytes; its byteOffset must be divisible by 2.
  • UNSIGNED_INT (5125) is 4 bytes; its byteOffset must be divisible by 4.
  • UNSIGNED_BYTE (5121) is 1 byte; this always satisfies alignment.

If an accessor referencing 32-bit floats starts at an odd byte offset inside its bufferView, the validator flags it because WebGL and Vulkan cannot perform unaligned memory reads efficiently.

BufferView Byte Stride Misalignment

When vertex attributes are interleaved inside a single bufferView, the byteStride property indicates the distance between consecutive elements.

The glTF Validator flags:

  • BUFFER_VIEW_BYTE_STRIDE_NOT_DIVISIBLE_BY_4
  • ACCESSOR_BYTE_STRIDE_MISALIGNMENT

According to the specification, byteStride must always be a multiple of 4 and cannot be smaller than the size of the largest attribute contained within the stride. For instance, if an interleaved vertex contains a 3D position (3 floats = 12 bytes) and a 2D UV coordinate (2 unsigned shorts = 4 bytes), the total byte stride is 16 bytes. If the attributes add up to an odd number, such as 14 bytes, padding must be added to reach a multiple of 4 (16 bytes).

Index Buffer Alignment Issues

Mesh indices are defined using scalar accessors with integer component types (5121, 5123, or 5125). Because index buffers frequently contain tightly packed 16-bit integers (UNSIGNED_SHORT), exporters often forget to pad the overall bufferView before appending subsequent vertex attribute data.

While 16-bit indices only require a 2-byte alignment for their accessor.byteOffset, the enclosing bufferView.byteOffset must still start at a 4-byte boundary. If consecutive submeshes share an index buffer or concatenate buffers improperly, the validator issues alignment warnings or errors.

How to Fix Alignment Errors

  1. Calculate Padding: Always pad binary data blocks to the nearest 4-byte boundary using the formula: \[\text{padding} = (4 - (\text{currentOffset} \pmod 4)) \pmod 4\]
  2. Standardize Struct Layouts: When interleaving vertex data, sort attributes by component size in descending order (e.g., vec4 floats first, followed by vec2 shorts, then bytes) to naturally minimize gaps while maintaining 4-byte boundaries.
  3. Verify Offsets Individually: Ensure that both bufferView.byteOffset (aligned to 4 bytes) and accessor.byteOffset (aligned to componentType size) satisfy their respective rules independently.
